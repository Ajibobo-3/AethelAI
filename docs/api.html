API QUICKSTART · V1

Make your first request.

Aethel provides an OpenAI-compatible chat completions route with customer API keys, a daily request quota, and persistent usage records.

V1 is a private API pilot. It is not a self-serve paid launch. Aethel does not charge customers yet; provider usage is billed to the operator’s Groq account. Groq rate limits still apply.

1. Configure the service

  1. Create a Supabase project and run both migrations in order: 202610230001_aethel_gateway.sql, then 202610240001_aethel_agent_beta.sql.
  2. Add the variables from .env.example to the Vercel project. Use your Supabase project URL and server-only secret key (SUPABASE_SECRET_KEY), GROQ_API_KEY, and a long random AETHEL_ADMIN_KEY. Keep these secrets server-side.
  3. Set AETHEL_ALLOWED_MODELS to the comma-separated public model IDs accepted by clients. The default inference model is llama-3.1-8b-instant.
  4. Redeploy, then confirm /api/health reports ready.

2. Agent model fallback

Before each run, the agent discovers the Groq account’s available Llama 3 text models. The primary is llama-3.1-8b-instant; if unavailable, the route retries with llama-3.3-70b-versatile, or selects an active discovered Llama 3 model. Standard aliases such as gpt-4o and gpt-4o-mini map to the primary.

3. Create a customer key

Run this from a trusted terminal. The admin key authorizes key creation. The generated customer key is returned once; store it securely.

curl -X POST https://www.aethelai.online/api/v1/keys \
  -H "X-Aethel-Admin-Key: $AETHEL_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"name":"my-app"}'

Save the returned api_key as AETHEL_API_KEY in your application’s server-side secrets. The database stores only its SHA-256 hash. Never put the admin key, provider key, or customer key in frontend code.

4. Send a chat completion

curl https://www.aethelai.online/api/v1/chat/completions \
  -H "Authorization: Bearer $AETHEL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "gpt-4o-mini",
    "messages": [{"role":"user","content":"Hello from Aethel"}]
  }'

The response follows the OpenAI chat completion shape. The gateway records the request status and token counts returned by the upstream provider. The default limit is 100 attempted requests per UTC day per key; provider errors also count. Set AETHEL_DAILY_REQUEST_LIMIT to change it. Output is capped at 2,048 tokens by default; configure AETHEL_MAX_OUTPUT_TOKENS to adjust that ceiling.

Routes and current boundaries

GET/api/healthService and dependency readiness
POST/api/v1/keysCreate a customer key (admin secret required)
POST/api/v1/keys/revokeDisable a customer key using its ID from the JSON body (admin secret required)
POST/api/v1/keys/topupIncrease a key's daily request cap or restore its configured default (admin secret required)
POST/api/v1/chat/completionsAuthenticated, metered chat completion with mapped Groq retry after primary HTTP 429
POST/api/v1/agent/runAuthenticated agent loop, up to five iterations, persisted session and tool steps

5. Run an agent task

Agent sessions are stored in Supabase and scoped to the customer key. The beta executes only the built-in calculator and get_utc_time tools; custom code and arbitrary tool names are not executed.

curl -X POST https://www.aethelai.online/api/v1/agent/run \
  -H "Authorization: Bearer $AETHEL_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"task":"What is 19 times 23?","session_id":"pilot-session-1","tools":[{"type":"function","function":{"name":"calculator","parameters":{"type":"object"}}}]}'

6. Top up a beta key

Use a trusted terminal and the admin key. Increase the per-key daily cap by a positive number, or restore the configured default cap. The endpoint retains usage history and does not erase request records.

curl -X POST https://www.aethelai.online/api/v1/keys/topup \
  -H "X-Aethel-Admin-Key: $AETHEL_ADMIN_KEY" \
  -H "Content-Type: application/json" \
  -d '{"id":"KEY_ID","increase_by":50}'

Streaming, payment collection, refunds, and distributed GPU execution are not implemented in this first release. Provider fallback is limited to a Groq retry after a primary HTTP 429, and requires the feature flag and a model mapping. Upstream usage and costs are charged by the configured provider account.
